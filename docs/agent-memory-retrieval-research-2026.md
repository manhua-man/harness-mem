## 2026-11-04：原 Oii 十九次调用的交付成本优化

原记录是 7 次候选查询／翻页＋12 次不同全文读取，实际消费者将这些 handler 调用放在 3 次 wrapper 执行中，另有首次提供的结果；不是 19 轮串行推理。[只读审计](../.tmp/completed-history-20261104/retrieval-optimization/call-audit.json)精确核对了原始计量：12 条没有重复全文；10 条完整对象反而比其预览、游标卡片便宜。两条后补查询虽然本例无最终新增采用，也不能据此推导可普遍无损删除。

本次不改排序、模型、数据或页预算。带 task_context 的人工 auto 查阅按实际 token 成本返回完整 statement 或预览；完整内容不再二次展开，报告归属与末尾条件完整保留。显式纯候选模式及自动 Hook/scheduler 仍只给预览。只有实际完整返回的条目计入读取反馈，相关性仍待 Agent 判断。

同一记录计划通过真实 current store/handler 回放，7 次发现不变，额外全文 12→2，总调用 **19→9**，返回文本 **24,771→17,835 tokens（约少 28%）**；全部原 12 条完整 statement 精确保留，含仅背景条目。这次把原先明确指定 candidates 的发现调用改用优化后的默认 auto，因此是已知选择计划的交付成本比较，不是新的首次盲测或总体准确率。源数据为按原时点筛选的 2,225 条当前行，不是历史数据库快照。

成本自适应最初仍为“全库是否能装进一页”计算全库卡片。随后改成按页渐进计算，并保留“末页去掉 continuation 后全部内容才放得下”的情况；新旧版本的实际页 payload 逐一相同。102 项游标、上下文与预算检查通过，另有报告归属及文档检查。[实际最终回放](../.tmp/completed-history-20261104/retrieval-optimization/same-plan-replay-final.json)和[最终静态／数据检查](../.tmp/completed-history-20261104/retrieval-optimization/final-checks.json)保留代码摘要及原／中间运行，不把不同进程冷缓存安排下的耗时差当作整体加速。未恢复安装、Hook/MCP/Router，未改真实知识或删除来源；全 Agent token、计费与真实宿主延迟仍未测。

## 2026-11-04：完结历史后的任务上下文召回（限定验收通过，仍未安装）

当前活动安排由 [roadmap](roadmap.md#current-iteration-plan) 维护。本次在既有 `search_memory` 增加可选完整 `task_context`，复用 current knowledge、候选预览、严格全文读和当前 Agent 的适用性判断。配置了本地模型时按语义候选顺序读取；普通无上下文和模型不可用时仍走词面检索，精确标题／正文读回优先。没有新服务、自动下载、旧 memory 表迁移或跨聊天的当前任务变量。上下文只作为查询输入，不证明用户批准。游标绑定完整上下文摘要、存储命名空间、算法与模型／预处理身份；返回 `reuse_arguments`，不反复输出整段前文。全文保留报告归属和末尾条件；相似度和预览不作事实或已读证据。

**保留的真实失败与原因。** 第一版原问题消费者用完六次额外补查和十二次全文，仍没找回旧的完整工具流程决定；[原报告](../.tmp/completed-history-20261104/retrieval-original/consumer-report.json)仍保留。只读排名诊断发现该目标原问题语义第 10、混排第 17；消费者某条实际自主查询语义第 6，却被混排推到第 11，超出该页前 8 条。去掉任务背景反而使这些实际查询更差，所以没有删除背景。语义流本已覆盖全部 eligible current rows，删除等比例词面插队没有丢候选；无语义通道仍有词面回退。

第一版固定六例还出现三次短信全文游标失效，独立评分为 [fail](../.tmp/completed-history-20261104/retrieval-holdout/gold-score-v1.json)。相同最终 2,267 行在冷全量／暖增量中有 544 条向量字节变化，词面顺序不变；批次组合使 int8 输出变化，是已复现的缓存历史依赖。逐 token 窗口独立编码并升级预处理身份后，全部向量、排序和游标指纹一致；没有放松严格游标。两次更早的夹具字段转换失败也保留，均不计为成功消费。前述失败不会被本次正结果覆盖。

## 2026-11-04：方面补查、项目身份与负例复核（仍未完成）

本轮源码修复了两个可独立复现的问题：全库去重现在保留相同正文的不同项目身份，同一项目内部的既有去重仍保留；任务态 Hook 和 MCP wake 在没有候选时也说明未命中并给出聚焦补查提示，预算过小时退回较短提示或原有精简响应。选中的全文仍按原查询、范围、项目身份及版本验证游标。`scope=project` 不扩大，`scope=all` 不按项目硬过滤；项目标签本身不能证明一条记忆适用于当前任务。

**显式任务上下文原型，未接入：** 上一次盲审实际发出的短查询 `局部优化` 不含原任务中的 Oii 主体。固定原型将原任务作为本次调用的额外线索，只从可核对的项目标签或标题标识符构建弱候选，并保留原查询的跨项目候选。它让目标进入 2,000-token 首屏第 6 条；另一 Agent 只看这批结果，打开 4 条全文，其中目标全文与原条目逐字一致，另一条直接相关，两条仅为间接背景。[原型选读审计](../.tmp/recall-quality-20261103/context-blind-audit.json)。这证明该固定短查询上的选读，不是首次自动召回或已接入功能。首屏同时多了两条并非直接答案的项目历史；2,290 行单 CPU 检索约由 0.11 秒增至 0.74 秒。

原型在已盲审的 32 条虚构补查上只读重放，按案例去重的有用候选 16→18、无关 4→5，项目限定未越界；这是事后开发对照，不是新盲评。随后新增的[冻结 8 例上下文盲评](../.tmp/recall-quality-20261103/context-v4/blind-score.json)刻意使用“间隔呢”“What range?”等依赖前文的省略式短查询，14 条标注有用记录中，原查询首屏 0 条，原型首屏 2 条有用和 1 条无关；独立 Agent 打开并采用 2 条有用，另外 7 例无候选。一次初始输出未捕获，报告依据重试后的完整输出；样本小且并非生产分布，但清楚表明仅补主体不能可靠恢复缺失的任务方面。原型没有实现上下文与游标绑定，也不能放入跨聊天共享状态；在同时改善有用发现与干扰、验证这一合同之前，不纳入运行时。

将相同原任务与短查询一起输入离线 int8 BGE 中文小模型，仅以相似度排序并按实际候选预算投影：这 8 例前 3 名累计有 12 条标注有用和 12 条无关；完整首屏覆盖全部 14 条有用，同时显示 30 条无关，项目限定范围外为 0。[对照结果](../.tmp/recall-quality-20261103/context-v4/semantic-score.json)无相关性或无答案阈值，也不是新的 Agent 盲评；48 条样例按项目范围排除 4 条后，模型加载和编码约 1.13 秒、容器峰值约 167 MB，不能当作完整库或 Windows 的运行成本。结合下节 2,295 行的 12.5 秒、约 394 MB 和虚构备份目标第 35 位的对照，这个模型没有接入运行时。

更严格的短查询提示没有证明原始 Oii 漏召回已解决。第一次独立盲审自主补查 8 次、打开 12 条不同全文；[回执审计](../.tmp/recall-quality-20261103/previous-guidance-blind-audit.json)确认关键的项目全流程约定没有出现在观察到的预览、搜索候选或全文中。第二次盲审按更短词组自主补查 8 次、打开 16 条不同全文，[回执审计](../.tmp/recall-quality-20261103/short-query-blind-audit.json)同样未发现该约定。评测者提出的 `oii 局部优化` 依然能在首屏第 5 条找到该项，并通过源码 handler 的游标逐字读回；这不是盲审 Agent 自主找到。两次盲审的输入为按原事件时间筛选的 2,290 条当前行，不是历史数据库快照。第二次盲审之后，源码提示恢复为保留必要条件的聚焦查询；尚未对该最终措辞重做独立盲审。

新的[冻结虚构盲评](../.tmp/recall-quality-20261103/verification-v3/blind-score.json)有 10 例、59 条记录，包含明确排除、混合正文、询问禁止事项、排查故障、无答案、项目限定和跨项目正例。按冻结标签，首屏出现 13 条有用和 7 条无关内容；独立 Agent 补查 32 次，打开 23 条标注有用和 3 条无关全文，最终采用 22 条标注有用和 1 条标注无关内容，4 条标注有用内容未采用，没有打开或采用被标为范围外的条目。无答案例中，它采用的相邻摆放建议未给出所问时长，Agent 明确没有据此推断时长。标签不是无争议真值：一条“有用”记录针对出芽前而题目询问新芽，另一条未采用记录与已用正文部分重复。一次误复制游标返回 `invalid` 后，Agent 用正确游标重试；评分只计实际成功打开。该测试针对当时的提示版本，不能扩展成最终提示措辞或自然宿主行为的验收。

自动按标点拆分原请求并交错词面子句的试验没有接入：原 Oii 的目标进入完整候选第 21 条，却仍不在 2,000-token 首屏，并挤出一条原首屏相关报告；已看过的 12 例开发集首屏有用候选 17→21、无关 14→20、范围外 2→4。[原案例回执](../.tmp/recall-quality-20261103/safe-test/container-runs/1793765211978460000-a6b11475ac6c4d51a1d96397821324f1.json)和[开发集回执](../.tmp/recall-quality-20261103/safe-test/container-runs/1793765229637060000-a1165b3b07724acf87d40b4a463f1169.json)只证明这次固定算法和样本的结果。类似地，按排除词将标题降序的虚构反例误降了正文含有用内容的混合条目，未合入过滤或排序。

[查询分解研究](https://aclanthology.org/2026.eacl-long.322/)提示分别衡量覆盖、噪声和阅读预算；[多条件检索研究](https://aclanthology.org/2026.findings-emnlp.1644/)提示拆分可能稀释同一答案必须满足的条件，故当前补查提示要求保留必要条件。两者不证明本地中文任务已解决。[E-SENS](https://aclanthology.org/2026.groundlm-1.28/)区分排除违例与召回，但其语义负信号和本地简单词面规则不是同一机制；本轮只吸收正反例分别计量，没有复制其重排器。[ReMe 固定版本说明](https://github.com/agentscope-ai/ReMe/blob/99ecdd24d14d0cf3f59ddcd5ffff738138fe6a2e/docs/en/memory_search.md)也提醒不同搜索通道分数尺度不同，不应把统一分数阈值当作相关性概率。EverOS 的补查思路仍由当前 Agent 承担，没有新增模型服务。

相关隔离回归 138 项通过；最终提示微调后，7 项受影响的针对性回归再次通过，Ruff 和 `git diff --check` 通过，不将重复检查加总为新用例。规范脚本在禁网临时副本中完成描述符再生成，原工作树中 `finalize_session_distill` 和 `govern_memory` 两项已有描述符与源码不一致，本轮没有覆盖这两项。测试容器不挂载用户目录或实时数据库；读取原案例时只在容器外以 SQLite 只读查询并经 stdin 送入容器，受保护 Hook 与 active-project 文件的前后哈希一致。全局和项目虚拟环境中的运行包仍未安装，不能据此宣称真实宿主 Hook 已验收。此前测试曾误注册六条用户级 Hook 命令并已移除；下节保留该事故与无法证明期间绝无触发的边界。

## 2026-11-04：聚焦查询与外部参考复核

源码已为“一个命名对象 + 一个较短中文复合主题”增加独立词面候选通道：分别检查该主题的短片段，要求对象精确出现在主题标题或项目标签，并与原排序交错；原跨项目结果仍保留。它只在读取入口启用，返回候选供选择，不给片段自动授予事实或指令权威；短主动搜索也可显式请求 `detail="candidates"`。当前 Agent 应对仍未回答的不同方面分别选择简短查询。条件、说话人和项目适用范围仍以完整正文及来源为准。

## 2026-11-04：长请求候选与按需读取（部分完成）

本轮源码中，长中文任务允许按局部词面片段扩大候选，不再要求一条记忆覆盖整段请求；这一扩展仅用于读取入口，不改变整理写入路径的默认比较。自动 Hook、任务态 MCP `wake` 和 `autopilot_search_tick` 输出明确标注为**不完整、未判断相关性**的预览，由当前 Agent 决定是否读取。长中文 `search_memory` 也先给预览；短的主动搜索仍可直接返回全文。预览保留项目及报告的说话人、时间，并提供与查询、范围、候选身份和版本绑定的全文读取位置；对象或结果变化会要求重新搜索，不会静默打开另一条。候选本身不计作完整阅读信号。即使短词或技术标识只有一条命中，自动入口也只返回候选：唯一词面命中不能证明适用当前任务。

这是干扰缓解，不是语义判断：预览本身仍可能造成干扰，Agent 也可能打开无关条目；短主动搜索仍可能返回多个无关全文。过小预算时提示聚焦搜索，不伪造候选或全文；空任务自动 Hook 不遍历记忆库。用户明确指定项目范围时，后续读取同样使用该范围与项目名；普通情况依旧跨全部项目，包含全局知识。

**此前的助手建议与当时的能力缺口：** 让当前 Agent 基于已有对话为需要历史信息的问题选择更聚焦的查询，并判断候选是否适用，避免为每次自动召回再启动后台模型。当时 `search_memory` 不能主动返回多条短候选并精确打开任意一条，普通 cursor 在结果变化时会重新显示第一页。上述新一节记录现已实施的候选与全文读取及其未通过之处。Hook 本身还可能按已有授权唤醒 Dream 续跑，不能把“普通 MCP 搜索不调用后台模型”扩大成“整个 Hook 没有后台工作”。

**输入与提示，源码已局部修复：** Codex 自动 wake 对已观察到的 `<in-app-browser-context source="ambient-ui-state">` 包装派生搜索条件，正常情况下只搜索后面的用户请求；原始 `current_task` 仍用于活动记录，不改变用户原文。用户写在请求里的 URL 原样保留；没有根据“这个页面”猜测使用内置浏览器 URL。请求直接提及标记或明显指向粘贴的浏览器上下文时，跳过任务态自动搜索，由 Agent 按需补查。其他宿主、手动搜索、格式不完整或不符合已知形态的包装保持原样。宿主 payload 是单个扁平文本项，无法仅凭这些字符串证明来源；用户粘贴相同包装但没有明显指代时，搜索条件仍可能误判。这是有界启发式，**不是可靠的原生来源识别**。

Host 提示把返回条数称为“候选记忆”，不再把数量当成逐条相关性证明。隔离测试覆盖原始包装形态、页面与 URL、用户拒绝内置浏览器、粘贴样本、普通历史引用、格式损坏、其他宿主、真实 wake 搜索调用链及活动身份。相关 **182 项测试通过**，Ruff 通过；这只证明源码与隔离路径，不代表安装后或自然宿主的行为已经验收。

**长中文排序仍未修好：** 单纯允许四字连续匹配的只读实验，使目标分阶段生成报告从未命中升到第 3，但不相关项目的“局部优化”排到第 1。按标点分句再做 RRF 的实验仍把不相关候选排在前面，且没有找回三个依赖聊天背景的报告。直接打开现有 source-context 宽松条件则得到 412 条候选，仍以不相关项目排首位。三种方案均未写入运行代码，不能把单例排名改善当作相关性修复。继续需要独立的正反例、准确的任务上下文和可解释的多路候选；跨项目相关知识与无关记忆必须同时检验。

**后台成本是另一条已观察到的问题：** 同一 Oii 聊天有 12 个 native source revision，后 11 个均为对前一版本的字节追加，并对应 12 个维护任务预算账本。完成的 83 次调用共记录 2,737,360 输入 / 415,483 输出 token、8,911.07 秒原生请求时间；另有 11 次失败，其真实用量未知。完成调用中 source 阶段 41 次、Dream 阶段 42 次。相邻两个任务的第一个结构分块 SHA256 相同，且各自的 source-decide 调用都完成。当前源码的常规路径对每个新 revision 向模型提供完整会话，已有知识只用于比较；这与记录强烈支持重复处理旧内容，但没有保留这两次的原始模型 prompt，也未核对当时安装字节，不能把历史发送的具体内容说成已逐字证明。每次 Stop 的新 generation 形成新的单任务预算，单批上限不是同一聊天的累计上限。[只读证据](../.tmp/recall-quality-20261103/background-cost-evidence-20261104.json)。

这些 token 和请求秒数不是前台等待时间、实际费用或资源争用的直接证明；用户所说的运行影响仍待具体症状与对应时序证据。下一步应验证追加修订的安全增量复用，确保前文条件、作者边界及后来纠正不会丢失，并检查后台任务的累计成本和重复 Dream；不凭上述观察擅自更改既有预算政策或把中断的历史任务视为成功。原始 Oii 问题的排序、相关性和真正可用性仍待修复和独立验收。

已完成调用的输入按阶段拆分：source-decide 12 次、296,774 token；source-verify 10 次、283,339；source-assimilate 10 次、1,141,316；source-final-scope 9 次、251,178；Dream 42 次、764,753。仅处理 decide 不能代表已经解决全部后台成本；也不能凭账本 token 总量断定归并阶段具体重复了哪些提示字段，历史原始 prompt 尚未证明。

增量修复不能只依据旧 job 的 completed 状态或相同 chunk 哈希跳过旧内容。现有 Dream source coverage 处理的是特定替换范围，不覆盖普通录入的全部作者类型；可借鉴其逐段审计、当前知识／来源版本和提交证据检查，但不能直接当作普通源完整性的证明。需要对严格追加和最后可能合并的 exchange 重新确认，对新内容引用、纠正、撤回或改变旧条件的情况重开相关旧范围；依赖不明、旧处置缺失或证据变化时回退完整审查。复用仍须经过现有核验、归并和最终写入门禁。现有 30 秒 idle 已能合并密集事件，简单加长等待并不能解决间隔较久的 revision 重复处理。

### 已查清的三层原因

1. **任务输入和宿主包装混在一起。** 2026-11-03 核对的 [host_entry](../harness_mem/host_entry/__main__.py) 从宿主 payload 取整段 prompt／user_message；[wake](../harness_mem/commands/wake.py) 将其作为任务 query。像 browser、app、ui、user、current、source、this 等环境词参与匹配。当时源码复算时，SkillPulse 的几条结果主要命中英文包装词，App Studio 的两条匹配 app／ui 或 app／agent，Oii 浏览器诊断匹配 browser／oii。报告标题与正文里固定的 “source report／user／current”等英文归属模板也参与排序，标题命中还有更高权重。这是输入与排序共同造成的噪声，原始各词历史分数不能事后编造；2026-11-04 的有限源码处理见上节。
2. **长中文 query 的过滤规则压掉了有用词。** [read_knowledge.py](../harness_mem/read_knowledge.py):232–255 将 query 生成的全部中文二字词放在一个整体上判断：须至少匹配一半，或者完整包含某一个连续中文段。这个原请求有 136 个二字词，前者须匹配至少 68 个；相关 Oii 报告只命中“生成／视频／漫剧”等数个词，且不含完整长句，因此这些中文命中被移除。反而《软西瓜》条目完整包含“上网搜”，被放行。去掉浏览器包装后，原来 11 条只剩 1 条，但该次 task 的生产链相关条目仍未找到，**说明只去包装不够**。
3. **自动查询没有带上已存在的任务背景，也没有任务级相关性确认。** 当轮文本以“管线”“三分钟漫剧”等概括为主；前面聊天谈到批量、时间线、导出，但 wake 的输入仅是本轮整段 prompt。普通排序是词法相似，随后直接把返回数称为“相关内容”；没有判断候选能否回答问题、是否仅是同项目的其他问题。时间预算分页发生在排序之后，不能纠正错误候选。

当前只读库中至少四条 Oii 报告的创建和最后更新早于该 turn，涉及分阶段生成、首次 AI 剪辑失败、手动成片限制，以及 H3 时间线素材 URI／保存修复。它们是**有作者与时期边界的助手报告**，不是本轮独立验证的当前产品状态。复算原始查询时这四条分别排第 1,299、1,306、1,324、1,262；仅搜索原用户请求中逐字出现的“三分钟漫剧”时，分阶段生成报告排第 2。再用后续反馈里概括的“批量生成／剪辑／导出／时间线”补全任务词，四条分别排第 2、5、10、3。后两项是受控诊断输入，不是当时系统执行的原始调用，也不证明所有类似任务都能靠短 query 解决。

**已确认的提示缺陷：** [wake.py](../harness_mem/commands/wake.py):168–171 的 selection_receipt 记录 matched_count／returned_count；[host_entry/__main__.py](../harness_mem/host_entry/__main__.py):1068–1073 直接把 returned_count 写成“已召回 N 条相关内容”。中间没有逐条语义相关性评审。这个数量是返回数量，不能被当成经评审相关数量。

**已确认的路径边界：** 有任务的自动 wake 用完整 current_task 对全部当前知识作文本排序；[read_knowledge.py](../harness_mem/read_knowledge.py):262–284 的相对覆盖阈值与多词／标识命中属于词法准入，不是“能回答当前核心问题”的判定。这足以解释为什么计数文案不能宣称质量，尚不足以确定原 11 条各自由什么词触发。

待查：原始查询是否混入背景文字、当时需要的管线经验是否已存、是否有相关候选在输出预算前被挤掉，以及每个噪声项的实际匹配理由。不得只凭结果就断言“提取遗漏”或“检索算法单独造成全部问题”。

### 对后续工作的修正

前次只完成研究文档，**没有完成 Lemma 两项吸收的实现或质量验收**；不能把“已经对照过外部参考”写成“已借鉴落地”。

本例要求先把当前召回挑选质量当作要解决的问题。真实解释是定位依据，改提示文案只是纠正承诺，两者都不能单独算精度修复。后续检验需要原始查询、应命中／应排除内容及跨项目有用的正例，先复现再改现有排序和选择 owner。

### C. 当前最直接的失败证据与因果

2026-10-21 最新保留首轮来自完整 87 轮来源。机械核对记录来源、原生返回与当前对照；独立语义审计仍判失败：

1. 本次执行与验收的两项临时要求被首轮选为规则；后续 session_only／no_write 阻止准入。这是该次准入保护成功，同时仍是首轮过选。
2. 来源中独立有支持的助手失败经验报告没有被提取：该助手报告 worker 退出后只有断点，没有恢复驱动时，单纯巡检不会推进；原生 wake 可以恢复原任务，并须保留原预算、切片及已提交结果等边界。这里证明的是该报告具有来源支持、值得有归属地保留，不是本轮复验当前恢复机制。审计认为已有当前正文没有完整等价内容。未产报告不能算作者归属已经改善。
3. 正常 installed MCP 当日能完整读回全部当前正文；这证明读回，不会逆转前两项首选失败。更早三份新增报告的有限准入／读回成功也继续保留。

证据：[独立语义审计](../.tmp/natural-source-closure-20261021/source-audit/first-selection-scope-author-fix/natural-first/independent-semantic-audit.json)（old_p8_core，187–201 行）、[终态机械回执](../.tmp/natural-source-closure-20261021/source-audit/first-selection-scope-author-fix/natural-first/terminal-actual-evidence.json)、[较早有限接受](../.tmp/natural-source-closure-20261021/source-audit/repeated-extraction-fix/natural-first/terminal-actual-acceptance.json)。详细历史仍由 [收敛合同](memory-write-convergence-20261020.md) 维护。

这几类失败不能混为一谈：

- **未存下**：没有当前等价条目，搜索再强也找不出；先处理提取遗漏或准入失败。
- **存错／条件丢失**：找到的记忆本身已失真，不能靠重排修复。
- **存对但没找回**：才属于查询、匹配、排序或输出预算问题。
- **找回但用错**：把当时助手报告当成当前事实，或把有限条件当成永久禁令，需要检查消费侧的证据使用。
- **门禁挡住错误**：只证明这次没有错误写入，不能抵扣上游过选、漏选及额外成本。

### F. 两项吸收的最小范围

**召回解释：** 复用当前搜索 owner，在实际排序时携带匹配词、覆盖／排序依据、范围及退路；按需关联现有来源与 verified_at。默认结果继续简洁，解释开关不应改变选点或排名。没有支持的理由就说明未知，不调用模型事后编理由。仅解释本次调用；要解释过去某次自动召回，必须有那一次真实记录，不能用新查询结果代替。

verified_at 记录验证时间，验证种类与范围须结合来源／验证记录解释，不承诺此刻重新核实外部世界；访问、被使用、验证与纠正保持分开。修正诊断中“非空即 sufficient”的含义，不增加一轮模型调用冒充充分性证明。无需新增解释数据库、服务或公开工具入口。

**失败经验：** 继续共用当前写入链。先用已有漏选反例检查首轮是否保留独立、有支持的机制；正文清楚表达方案、失败依据和适用范围，来源明确支持时保留重试条件。未给出的原因、环境或重试条件标未知，不能为了四项齐全补造。一次失败不是永久禁令，临时进度也不因为写成“教训”就有长期价值。

先保留正文和来源合同，不立即增加四个强制字段或独立失败库。检验归并、更新及 Dream 前后是否保留支持的条件与例外；更严格拒绝与更完整保留要同时成立。相似任务召回先在已保存内容上验证，不能许诺主动防重试或自动阻止操作。

### G. 如何判断“改善了好用性”，以及建议顺序

复用现有 qualification／测试与收据位置，不另建评测平台。先从已知正反例开始；既用被修复样本，也用未参与修改的保留样本，避免只对熟悉措辞有效。

| 验收问题 | 最小对照与通过含义 |
| --- | --- |
| 应记与不应记是否同时做好 | 在完整来源中同时放可复用失败机制、一次性要求、真实长期纠正。逐项人工核对首轮选择、最终决定及入库结果；安全不写不能抵扣遗漏。 |
| 条件在更新中是否保住 | 相同失败原因在同条件、条件改变、原因未知时分别处理；核对归并／替换／Dream 的最终全文，不能变成永久禁令或无根据的恢复承诺。 |
| 已存下但换措辞能否找回 | 同一已验证库使用原词、中文自然问法、技术标识及合理改写，标记必须命中和必须排除；无法找回先看真实匹配解释，再决定是否需要小型检索增强。 |
| 找回后是否真的影响正确操作 | 相同任务分别用无记忆、当前记忆、正确来源上下文对照。核对下一步动作和条件，而非只会复述；oracle 只用于隔离诊断，不进入生产路径。 |
| 解释是否真实且有用 | 开／关解释返回相同结果和顺序；展示的匹配与实际算法一致。范围、查询、当前条目改变时解释随之改变；缺来源、未核验、直接读指定条目不能编出支持。 |
| 长库与成本是否可接受 | 固定正确证据，逐步增加无关内容；共同记录错误、噪声、返回正文 tokens、调用数、尾部等待和失败／未知用量。限定在能保质的预算内；不要通过丢必要条件或默认全量注入换分。 |

成本分开报告构建／维护、检索、答案生成，返回上下文 tokens 与原生模型 input／output、累计请求秒与用户等待不可混记。按真实 tokenizer 或明确的保守计量方式报告，不把字符估算冒充实测 token。模型、来源、预算和消费者保持一致，失败尝试也计入。

建议顺序：

1. **先校准现有证据与探针**：把同一过强断言导致的两个失败测试记为待修正，建立已知漏选／过选的最小对照，不把修探针计作语义改善。
2. **在现有搜索中补可选真实解释**：小范围实装并验证不改默认结果；用它定位已保存内容的漏召回，消除空泛充分性标签。
3. **针对现有失败经验漏选与条件保留改进**：同时保住来源归属、临时范围和已有成功样本；经过隔离真实模型链路与普通 MCP 全文回读后，才能接受对应语义改善。
4. **用未参与调试的相似任务和干扰增长复核收益**：收益不成立就缩小或撤回改动，不因为引用了新论文继续扩架构。

这只是建议的实施顺序，用户尚未在本轮要求执行新模型测试、共享安装或真实记忆维护。后续具体执行应回到现有活动计划，保留其原有失败、预算和未决范围；不重置旧账。

## 2. 2026 前沿共识

[MemoryData（arXiv:2606.24775）](https://arxiv.org/abs/2606.24775)（2026-06-23）将 agent memory 拆为四模块：

```text
representation & storage  →  持久表示 + canonical 状态
extraction                  →  从对话/证据写入结构化记忆
retrieval & routing         →  按需检索与路由
maintenance                 →  合并、失效、压缩、生命周期治理
```

**实证结论：**

- 没有单一架构通吃所有 workload；效果取决于 **memory 结构与瓶颈是否对齐**。
- **Localized maintenance** 比全局重组更省成本（与 harness-mem dream + ledger 方向一致）。
- 现有评测多用端到端任务指标（F1/BLEU），把系统当黑盒，**检索精度、更新正确性、隔离、成本** 测量不足。

[Tenure / PrecisionMemBench（arXiv:2605.11325）](https://arxiv.org/abs/2605.11325)（2026-05）进一步指出：

- LoCoMo 等测的是「模型答对了没」，不是「memory 检索对了没」。
- 返回整个 belief store 可得 recall=1.0，仍能通过 answer-quality 评测。
- 领域语料上 **纯 cosine similarity precision 约 0.05–0.08**；换 20× 规模 embedding 无法根治。
- 需要 **retrieval-isolated** benchmark：`mustExclude`、`scope`、`supersession` 等硬断言。

## 3. 对标项目

### 3.1 Mem0

**来源：** [Search 文档](https://docs.mem0.ai/core-concepts/memory-operations/search)、[AI Memory Benchmarks 2026](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)、[State of AI Agent Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)

**管线：** query processing → vector search → filters/rerank → metadata delivery

**2026 算法要点：**

- Multi-signal retrieval：semantic + BM25 + **entity boost** 并行融合
- Platform v3 **Temporal Reasoning**（时间有效性）
- OSS `explain=True` 暴露 `score_details`（semantic、BM25、entity、threshold）
- **scope/filter 一等公民**：`user_id` 等硬过滤，防跨用户污染

**Benchmark 叙事：** LoCoMo、LongMemEval、BEAM——测 multi-session continuity，但应 **成对报 accuracy + token/latency**；不等于 retrieval precision。

**借鉴：** filter-first、explain 分项、entity boost、temporal。  
**不照搬：** 云托管全栈、大而全 CLI。

---

### 3.2 Zep / Graphiti

**来源：** [Searching the Graph](https://help.getzep.com/searching-the-graph)、[Observations](https://help.getzep.com/observations)

**检索：** semantic + BM25 + **RRF**；可选 BFS、MMR、`node_distance` reranker

**数据形状：**

- **Facts**：边级、带时间戳的细粒度声明
- **Observations**：跨实体、证据支撑的 durable 模式（自动派生、dedup、supersede 退休）
- **Auto search**：跨 edges/nodes/episodes/observations 并行检索 + cross-scope rerank，打包 `context` 块

**Temporal：** `valid_at` / `invalid_at` / `expired_at` 等 filter——**metadata 失效**，不是评分衰减

**借鉴：** relation/decision 的 graph boost 思路、observation 层、temporal invalidation、cross-scope 多样性  
**不适合现在：** 完整图数据库替换 SQLite runtime

---

### 3.3 Letta

**来源：** [Archival memory](https://docs.letta.com/guides/core-concepts/memory/archival-memory/)

**分层：**

- **Core memory blocks**：常驻上下文、频繁变更状态
- **Archival memory**：语义可搜 DB，**仅通过 tool 按需查询**，不塞进 context window

**借鉴：** harness-mem 的 wake（紧凑 brief）+ search（按需深查）分层  
**产品哲学：** 长期记忆不应默认全量注入 prompt

---

### 3.4 sqlite-vec

**来源：** [Hybrid search](https://alexgarcia.xyz/blog/2024/sqlite-vec-hybrid-search/)、[Metadata filtering](https://alexgarcia.xyz/blog/2024/sqlite-vec-metadata-release/)

**栈：** FTS5 + vector + RRF，单文件 SQLite，metadata 列预过滤

**判断：** 与 harness-mem 现状最接近的 **短期实现路径**；不必为 benchmark 未证明的瓶颈换引擎。

---

### 3.5 Tantivy

**来源：** [Tantivy](https://github.com/quickwit-oss/tantivy)

**定位：** Rust embedded 全文库，非产品层

**判断：** 仅当 SQLite FTS 在 scale benchmark 中确为瓶颈时，作为 **optional Rust 加速** 考虑；不作默认替换。

---

### 3.6 vstash（学术 + 同栈参考）

**来源：** [arXiv:2604.15484](https://arxiv.org/abs/2604.15484)（2026-04）

**栈：** sqlite-vec + FTS5 + RRF + adaptive per-query IDF weighting

**正面：**

- Adaptive RRF 在 BEIR 五数据集全涨（ArguAna 最长 query +21.4%）
- Vector distance 作 relevance/confidence signal（优于 score spread）
- Disagreement-mined embedding 微调（无标注 hard negatives）
- 50K chunks 中位延迟 ~20.9ms

**负面结果（重要）：**

- post-RRF 的 frequency+decay、history boost、**cross-encoder rerank** 均未提升 NDCG

---

### 3.7 Tenure（2026 前沿对照）

**来源：** [arXiv:2605.11325](https://arxiv.org/abs/2605.11325)、[precisionmembench](https://github.com/tenurehq/precisionmembench)

**主张：** precision-first、structured belief、hard scope isolation、multi-path BM25（analyzer asymmetry + alias boost）

**Benchmark：** 89 cases，scope / mutation / isolation / session drift；**不经过 LLM** 评 retrieval precision

**与 harness-mem：** 方法论高度相关（Truth canonical、project isolation、supersede）；纯 BM25 路线与现有 hybrid 栈不同，宜 **借鉴评测与 Truth 结构**，非替换 SearchFacade。

## 6. 改进方案（P0–P3）

**原则：** 不换 SearchFacade / SQLite；先可测，再小步增强。

### P0 — 建立基准（1–2 周）

建 **retrieval-isolated** golden suite（约 80 条），**不经过 LLM** 打分。

| 类别 | 验证点 |
|------|--------|
| truth / observation / relation / decision | 各 `source_kind` 命中率 |
| project_isolation | 跨项目泄漏 = 0 |
| temporal_current / temporal_history | supersede 默认排除 vs 显式历史 |
| abstention | 不存在事实不误召回 |
| vector_off | FTS-only 退化可接受 |
| scale_smoke | 1k / 10k / 100k 延迟（可选） |

**指标成对报：** R@5 + p95；isolation leak rate；vector_off ΔnDCG@5。

**交付物：**

```text

```

### P1 — 算法小步（benchmark 驱动，逐项 A/B）

| 顺序 | 项 | 参考 |
|------|-----|------|
| 1 | Filter 前置加固（project / truth_status / temporal_scope） | Mem0、Zep、Tenure |
| 2 | Adaptive IDF RRF | vstash 2604.15484 |
| 3 | Vector distance 置信度 / abstention tier | vstash |
| 4 | 同源 MMR 去重 | vstash、Zep MMR |
| 5 | 1-hop relation/decision boost | Zep BFS-lite |

**明确不做：** post-RRF 时间衰减评分、默认 cross-encoder rerank、换 Tantivy/LanceDB。

**主要改动文件：** `harness_mem/search/backend.py`、`harness_mem/search/hybrid_search.py`

---

### P2 — 可选 Rust 加速（P0 证明热点后）

仅当 benchmark 显示热点 >10% query 时间：

- RRF fusion 算术
- bulk derived-index row build
- benchmark runner 编排

**入口：** `harness_mem/rust_core.py` optional facade；**不替换** SQLite 查询层与 SearchFacade。

---

### P3 — 中期（golden 稳定后）

- Disagreement-mined embedding 微调（vstash）
- `retrieval_quality.py` 的 temporal/multi_hop fanout 用 golden 验证收益后再默认化

## 7. 当时建议继续加厚什么

与 v4 §5、README 一致；调研补充如下。

### Truth

- 统一返回 `truth_status`、`temporal_scope`、`source_kind`
- supersede **存储层失效** + 默认 search 只 current
- review inbox / state audit 叙事写进对外文档
- 可选：truth 级 `why_it_matters`（wake 行为指令，非裸 fact）

### Retrieval（产品可见部分）

- recall contract 完善：`evidence` / `sources` / `steps` / `status`
- project isolation 结构化；`scope=all` 按 project 分组
- 空结果 / 低置信语义（`empty` / `low_confidence`）
- **不新增** MCP 工具；加厚 metadata 与 explain

### Maintenance

- 仅强化 **dream**：auto gate、ledger、undo
- dream 产出尽量走 supersede **audit**，非静默改 truth
- CLI 保持 operator console；purge/rebuild 不进 Daily workflow

### Recall contract

- 读路径解释层；**不**创建 candidate、不 confirm truth
- 与 `record_context_outcome` 形成闭环

### 对外宣称边界

**宣称：**

```text
local-first · auditable · one hm entry
truth canonical · index rebuildable · vector optional
dream = default maintenance (ledger + undo)
single public MCP surface
```

**不宣称：** LoCoMo/BEAM 榜单、Mem0/Zep 全替代、graph DB 默认检索、MCP profile 选择、Rust 作为产品版本号。
