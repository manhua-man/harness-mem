# harness-mem v2.4 Maintenance CLI

> Operator reference for the v2.4.3 maintenance CLI surface: the four
> `harness-mem config` subcommands and the two
> `harness-mem integration install-*-hook` subcommands.
>
> This file is the canonical operator doc; the generated IDE hook headers point
> back here via their `Docs:` line. Per-command `--help` output stays the source
> of truth for exact flags — this page cross-links rather than duplicating each
> docstring.

## The v2.4 CLI is maintenance-only

The `harness-mem` console script in v2.4 is a **maintenance console**, not a
business surface. It exists so a human operator can manage configuration and
install hooks. It does **not** expose reflection, distill, ingest, wake, or any
other memory business command.

Business commands run exclusively through one of two paths:

- **MCP** — an in-session agent calls the MCP tool, which maps to the shared
  implementation (this is how `/hm:distill` and friends run).
- **`python -m harness_mem.host_entry`** — the v2.4.1 host entry, invoked by an
  IDE hook or a scheduler.

There is deliberately **no `harness-mem reflection`, `harness-mem distill`,
`harness-mem ingest`, or `harness-mem wake` subcommand** (v2.4.0 Req 10.2,
re-asserted by v2.4.3 Req 8.5). Generated hooks invoke
`python -m harness_mem.host_entry`, never the `harness-mem` console script, so
the runtime stays decoupled from the CLI executable.

## Triggers default to off

v2.4 ships with all triggers **off**:

| Key | Default | Meaning |
| --- | --- | --- |
| `triggers.after_agent` | `off` | IDE after-turn host trigger |
| `triggers.scheduler` | `off` | scheduler/cron host trigger |
| `distill.mode` | `defer_to_agent` | what the host trigger does after ingest/prepare |
| `worker.mode` | `off` | long-running worker gate (`on` enables the config path; current runtime still ships no default always-on daemon installer) |

Installing an IDE hook does **not** by itself enable reflection. With
`triggers.after_agent = off`, the hook runs the host entry and the host entry
exits 0 without writing any job or candidate. You opt a project in explicitly:

```bash
harness-mem config set triggers.after_agent on --scope project
```

## `config` subcommands

All four `config` subcommands route every read through the v2.4.1
`load_merged_config(project_root)` loader and every write through
`harness_mem.config.writer.set_value`. The CLI never re-implements deep-merge,
default-fill, or schema validation — that logic lives once in the config
package, so the CLI, the host entry, and `doctor` never disagree.

Recognized keys and their allowed values come from the v2.4.1 `MergedConfig`
schema:

| Key | Allowed values | Default |
| --- | --- | --- |
| `triggers.after_agent` | `off`, `on` | `off` |
| `triggers.scheduler` | `off`, `on` | `off` |
| `distill.mode` | `defer_to_agent`, `inline`, `worker` | `defer_to_agent` |
| `worker.mode` | `off`, `on` | `off` |

`--project-root PATH` is optional on every subcommand; when omitted, the
project-level Config_File lookup uses the current working directory.

Config files:

- User-level: `~/.harness-mem/config.toml`
- Project-level: `<project_root>/.harness-mem.toml` (overrides user-level)

### `config get <key>`

Read-only. Prints the single resolved value for a dotted `<key>` to stdout and
exits 0. A recognized key absent from both files resolves to its declared
default. An unrecognized key that is present in neither file prints
`key not found: <key>` to stderr, exits 1, and produces no stdout.

```bash
harness-mem config get triggers.after_agent
```

### `config set <key> <value> --scope {user,project}`

Writes one value to the chosen Config_File, creating the file (and the
`~/.harness-mem/` parent directory for user scope) if absent. Other existing
keys are preserved. `--scope` is required.

- On success: prints `wrote <path>: <key> = <value>` to stdout, exits 0.
- On a recognized key with an out-of-range value: prints
  `invalid value: <key> = <value>; allowed: {<set>}` to stderr, exits 1, and
  writes nothing.
- On a filesystem error: prints `write failed: <path>: <error>` to stderr,
  exits 1.

```bash
harness-mem config set triggers.after_agent on --scope project
```

**v2.4.3 limitation — no `--unset`.** `config set` only writes values; it cannot
delete a key. Removing a key requires hand-editing the TOML file. Writes also do
not preserve comments or key ordering (the file is round-tripped through a
structured dict), so operators who care about layout should hand-edit instead.

### `config list`

Read-only. Prints every recognized key with its resolved value plus a source
label (`default`, `user`, or `project`), followed by any unrecognized keys
present in either file with their source. When neither Config_File exists, it
prints the header note `no Config_File found, showing defaults` and then the
defaults. Always exits 0 in non-error cases.

```bash
harness-mem config list
```

### `config validate`

Read-only. Runs the full v2.4.1 `load_merged_config` pipeline against the
resolved Config_File set — the same loader the host entry and `doctor` use, so
validation outcomes never diverge across the three surfaces.

- On success: prints `config valid: <project_root>` to stdout, exits 0.
- On a TOML parse error: prints `parse error: <path>: <reason>` to stderr,
  exits 1.
- On a schema violation: prints `invalid value: <key> = <value> at <path>` to
  stderr, exits 1.

```bash
harness-mem config validate
```

## `integration install-*-hook` subcommands

Both installers generate a small shell hook that invokes
`python -m harness_mem.host_entry --source ide_hook ...` with the target repo's
absolute path baked in at generation time. The generated file never contains a
`harness-mem` console-script invocation (Req 5.3 / 6.3); an internal boundary
self-check rejects any template that would violate this before writing to disk.

Each generated hook carries a comment header naming the generating harness-mem
version, the generation timestamp, and a `Docs:` pointer back to this file
(`docs/cli/v2.4.md`). The doc pointer is supplied by the install handler so the
authoritative location is owned in one place.

Common flags:

- `--project-root PATH` — optional; defaults to the current working directory.
- `--force` — overwrite an existing hook. Without it, an existing hook is left
  untouched and the command exits 1 with
  `hook already exists: <path>; use --force to overwrite`.

On success each prints `installed: <path>` to stdout and exits 0. On a
filesystem error each prints `install failed: <path>: <error>` to stderr and
exits 1.

### `integration install-cursor-hook`

Generates the Cursor after-agent hook at
`<project_root>/.cursor/hooks/after-agent.sh`.

```bash
harness-mem integration install-cursor-hook
```

### `integration install-claude-hook`

Generates the Claude Code after-turn hook at
`<project_root>/.claude/hooks/after-turn.sh`.

```bash
harness-mem integration install-claude-hook
```

## How hooks relate to the MCP `/hm:distill` follow-up

Installing a hook only wires the plumbing. The end-to-end flow is:

1. **Install** the hook for your IDE (`integration install-*-hook`). This alone
   does nothing at turn end yet — triggers are still `off`.
2. **Opt in** for the project:
   `harness-mem config set triggers.after_agent on --scope project`.
3. **At turn end**, the IDE runs the hook, which calls
   `python -m harness_mem.host_entry`. The host entry reads the merged config; if
   the trigger is `off` it exits 0 with zero side effects.
4. **When enabled**, the host entry runs the `reflection_once` business command
   (ingest + prepare, writing a job). With the default `distill.mode =
   defer_to_agent`, it does **not** run an LLM — the job is left marked
   `needs_distill`.
5. **Later, in an agent session**, you run **MCP `/hm:distill`** (or the
   equivalent MCP tool). That step does the LLM distillation and writes the
   resulting suggestions into the candidate layer for review. The hook never
   writes confirmed truth and never calls an LLM directly.

So the hook is the cheap, non-blocking "capture" half; the MCP `/hm:distill`
main loop is the "process and review" half. Hook failures always exit 0 and
never block the IDE turn — inspect outcomes with `harness-mem doctor` (v2.4.2),
not via hook output, which is suppressed.
