# 0.9.11 - Effective Memory Closure

## Goal

Turn the existing safe memory machinery into a timely, measurable user-value
loop without weakening the lossless evidence boundary or adding another public
surface.

```text
captured
  -> offered
  -> claimed
  -> checkpointed
  -> verified
  -> finalized
       |-> no_candidate (successful terminal)
       `-> promoted -> searchable -> surfaced
                                      -> used / ignored / misleading /
                                         missing_feedback
```

The release is successful when a normal Agent task can consume a bounded batch
of fresh session work, retrieve useful memory at an explainable cost, and leave
enough content-free evidence to show where the loop succeeded or stopped.

## Product contract

The user-facing promise is:

> Start working normally. harness-mem brings back relevant history and records
> reusable outcomes. Review and undo remain explicit escape hatches.

The five-stage internal loop remains compatible, but it is not presented as a
manual daily checklist. No eighth host, public MCP tool, persistence root,
truth store, background semantic worker, or automatic destructive action is
introduced.

## What already exists

- Immutable native transcript revisions, hash-verified chunks, resumable
  checkpoints, and exact raw reconstruction.
- A compact distill projection that indexes every exchange, preserves the final
  exchange and risk/memory signals, uses head/tail previews, and exposes complete
  semantic-window and raw-proof drilldown.
- A two-slot Agent-active queue with 3:1 recent/oldest fairness, daily offer
  budget, restart recovery, backoff, and terminal `promoted` / `no_candidate`
  dispositions.
- Evidence-basis and verification-outcome admission, current-repository digest
  checks, contradiction handling, audit/undo, and receipt-first source cleanup.
- Retrieval shadow signals for surfaced results and explicit
  `used` / `ignored` / `misleading` outcomes.

## Upstream comparison: what "3k" actually meant

The 2026-08-04 external compact-manifest implementation is a
useful product signal, but not the algorithm to copy. It estimates 3k as
`budget_tokens * 4` characters, reduces each turn to at most 150 user
characters, six tool signatures, and 200 answer characters, then appends turns
in order until the next block does not fit and stops with `break`. Later turns
are absent from that manifest, and no model tokenizer verifies the claim.

harness-mem keeps the useful idea—give the Agent a compact first-pass
manifest—but preserves every exchange index, uses head/tail previews and
evidence anchors, and keeps full semantic/raw drilldown. The response target is
measured against the exact serialized MCP text, not a character proxy.

## Scope

### 1. Honest adaptive response budgets

`budget_tokens` is a soft target for the complete compact MCP payload, not a
promise that only the nested semantic evidence is measured. The runtime must
record both the evidence projection and final serialized result:

```text
requested_target_tokens
evidence_tokens
protocol_tokens
serialized_tokens
tokenizer
outcome = within_target | expanded_for_complete_manifest |
          expanded_for_explicit_drilldown | expanded_for_full_detail |
          expanded_for_required_metadata
```

The number `3000` remains a compatibility default for compact distill calls,
not a product invariant. Callers may request a larger target. A complete indexed
manifest may exceed the target rather than silently dropping exchanges; the
expansion must be explicit and the full payload must avoid redundant copies.

The compact projection keeps its current coverage-first behavior:

1. Every exchange retains an index and signal flags.
2. The final exchange and risky/high-value exchanges receive larger previews.
3. Previews retain both head and tail plus evidence anchors.
4. Complete semantic windows and raw proof remain separate drilldowns.

### 2. Bounded Agent batch

One Agent-capable opportunity may offer and process between one and three jobs.
The batch size is bounded by the existing active lane, daily offer budget, and
an explicit per-opportunity token/work limit. Each job retains independent
identity, lease, checkpoint, review, finalization, retry, and cleanup state.

- Default automatic opportunity: up to two jobs.
- Explicit `/hm:distill`: up to three jobs when requested and eligible.
- User-task response remains ahead of maintenance instructions.
- A failure or defer affects only that job.
- The existing 3:1 recent/oldest selection invariant remains authoritative.
- No Agent means `waiting_for_agent`; no semantic work is claimed in the
  background.

### 3. Content-free value funnel

Reuse `SessionDistillJob`, `RetrievalSignal`, the local event log, and existing
status surfaces. Add only additive fields/signal kinds needed to correlate:

- Agent offer and claim;
- first/last checkpoint progress;
- terminal disposition and searchable truth count;
- wake/search surface receipt;
- explicit outcome or `missing_feedback`.

Surface and outcome receipts correlate by the content-free pair
`retrieval_id + target_id`. One used source does not manufacture positive
feedback for another source returned by the same retrieval.

No missing outcome is inferred as `used` or `ignored`. Compact status reports
only the current bottleneck and totals; full status reports stage conversion by
source-session host plus actionable reasons. Distill stages use a seven-day
job-created cohort; retrieval feedback uses the same seven-day observation
window, and both scopes are named in the response.

### 4. Default-surface convergence

README, Quickstart, and generated Daily assets describe three user intents:

1. continue work;
2. remember a reusable result;
3. review or undo an incorrect memory.

Status, distill, and Dream remain compatible operator/audit entries. The exact
27-tool MCP allowlist and seven installed host surfaces remain unchanged.

## Architecture

```text
native host transcript
        |
        v
immutable revision/chunks ---------> raw proof drilldown
        |
        v
coverage-first exchange manifest --> complete semantic windows
        |                                  |
        +--------------+-------------------+
                       v
             per-job verify/finalize
                       |
                       v
                canonical truth
                       |
                       v
wake/search receipt -> surfaced -> explicit outcome
        ^                                  |
        +---------- status funnel <--------+
```

Shared-contract ownership:

- MCP response-budget receipt and serialization accounting: main thread.
- Agent batch selection/offer contract: distill lifecycle and session store.
- Funnel aggregation: runtime/integration health and response views.
- Host instructions and public docs consume the stable contracts after code
  acceptance; they do not define runtime behavior.

## Failure modes and rescue

| Failure | Required behavior | Rescue |
|---|---|---|
| Minimum complete manifest exceeds target | Return all exchange indexes and mark explicit expansion | Drill into selected windows; request larger target if useful |
| Explicit full/raw drilldown exceeds compact target | Preserve explicit user intent and mark full-detail expansion | Caller narrows exchange/chunk indexes |
| Batch job fails | Defer/back off only that job | Continue remaining offered jobs within opportunity budget |
| Batch opportunity is interrupted | Keep completed checkpoints; do not mark unfinished jobs terminal | Resume exact job ids on next Agent opportunity |
| Offer has no outcome | Count `missing_feedback`, never infer utility | Host/Agent may record outcome later using the receipt |
| Funnel write fails | Memory/search operation continues; return content-free degraded state | Status identifies the missing stage/write failure |
| Host copies drift | CI/install sync fails with exact affected host | Regenerate from canonical assets |

## Acceptance gates

### Budget and manifest

- Every exchange remains represented in compact semantic evidence at all
  supported target sizes.
- Final/risky/high-value exchanges keep larger head/tail previews and stable
  drilldown indexes.
- Compact responses report actual serialized tokens and explain every target
  expansion.
- No compact response repeats the same full content in multiple top-level
  fields.
- Explicit full/raw audit remains available and is never silently downgraded.

### Batch and freshness

- One Agent opportunity can offer two independently addressable eligible jobs;
  explicit deep distill can request up to three.
- Offer, claim, checkpoint, defer, finalize, and retry remain project-isolated.
- A 32-session deterministic burst reaches terminal or machine-readable
  backoff outcomes in at most 16 two-job Agent opportunities.
- The oldest lane receives an opportunity at least once in every four new lane
  selections.

### Funnel and feedback

- Full status reports offered, claimed, checkpointed, finalized, searchable,
  surfaced, feedback, and missing-feedback counts for the selected window.
- Every stage is content-free and project-isolated.
- `surfaced` without an explicit result increments `missing_feedback`; it never
  changes ranking as positive or negative feedback.
- Existing explicit outcome signals retain their bounded, explainable ranking
  influence.

### Compatibility and quality

- Exact 27-tool MCP contract and seven-host installed-command contract pass.
- Existing single-job clients remain valid.
- Complete Python, Ruff, Mypy, Rust, package, fresh-install, and host-replay
  gates pass.

## Not in scope

- Fixed 3k responses across hosts or tasks.
- Semantic ranking from clipped manifest text.
- Automatic raw-source deletion or shared-container mutation.
- A second queue, scheduler, dashboard command, truth store, or MCP profile.
- New embedding/RRF defaults, another search engine, or more Rust without a
  measured bottleneck.
- Clearing every historical parked job by lowering evidence or governance
  standards.
