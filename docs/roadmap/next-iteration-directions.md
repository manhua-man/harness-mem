# 后续迭代方向（探索中，未排期）

本文记录 `0.9.22` 之后值得研究的方向。它不是已批准的实现计划，不
授予网络访问、真实历史记忆变更或自动迁移权限，也不为下一个版本号作出
承诺。具体方案须在实施前单独定稿、评审并取得相应操作授权。

## 共同边界

- 正常 `wake` / `search` 继续只返回干净的当前长期知识；候选、来源、
  任务、回执和内部 ID 不得进入默认结果。
- 不把搜索结果、模型判断或旧数据库状态本身当作事实证明。
- 不默认访问会话中出现的外部链接，不默认重蒸馏、删除或改写真实历史记忆。
- 所有 durable truth 变更继续走“逐点验证 → 归纳吸收 → 可撤销 mutation”
  的同一条路径。

## 方向 A：外部网页与 API 的真实来源复核

**主要模块：** 2. 逐点验证；由 Dream / Review 在 3--4 的治理反馈环中
触发。

### 想解决的问题

当前系统可以复核 transcript、用户陈述和本地仓库/文件，但一条知识若依据
官网文档、公共网页或 API 的当时状态，不能只凭旧摘录或旧验证结论宣称它
仍是当前事实。

目标不是做通用搜索引擎，而是复查该知识原先声明的**具体来源**：

```text
当前知识 + 最小外部来源定位 + 待核对断言
→ 重新访问同一网页或安全的只读 API
→ 该来源是否仍支持此断言？
→ 保持 / 提议修订 / 标为过期或待确认
```

例如“某 API 单次最多接受 100 条记录”应复核同一份官方文档或受限 API
响应中的相应字段；网页改为 50、来源消失、权限不足或网络失败，都不能被
伪装成“验证通过”。

### 需要先定下的设计问题

- 外部来源合同的最小形态：网页 URL 与可复查正文/结构断言、API endpoint
  与允许的只读请求模板、预期字段或响应断言分别如何表示。
- 哪些来源允许网络复查、何时复查、如何显式授权；认证信息如何仅从本机
  安全配置读取而不进入知识或审计正文。
- 页面重定向、正文结构变化、限流、访问失败、内容模糊和来源相互冲突时，
  分别应得到 `STALE`、`PARTIAL`、`UNANSWERED`、`CONTRADICTED` 还是
  `NOT_APPLICABLE`。
- 如何保留足够的最小来源定位以便复查，同时不把抓取正文、密钥或无关网页
  内容变成长期记忆。
- 复核周期、Dream 的自动触发与人工 Review 的关系，以及“复查失败”是否
  应影响检索排序和展示措辞。

### 明确不做

- 不爬取或搜索会话里所有链接。
- 不让搜索结果自动替换原来源或自动写入长期知识。
- 不让 provider 直接访问网络后自行宣告某条知识为当前真相。

## 何时从方向进入施工

这个方向须先产出具体设计、最小可验证 slice、隔离 fixture 和停止条件；
再决定是否排入版本。它不应被扩张为一个大而不可回滚的“记忆重写”版本。
