# harness-mem v5.6 Multi-client Field-test Packet

> 这是跨客户端发版前扮演脚本，不是营销 persona，也不是自动测试。执行者需要真的在对应客户端里扮演用户，只读白名单文档，逐条记录可观察结果。

## 共用扮演纪律

- 忘记你是项目维护者；不要读源码来补文档空洞。
- 只读 persona 白名单里的文档和客户端里 agent 返回的内容。
- 每一步都记录原文错误、工具返回字段、首次成功时间和你下一步是否明确。
- 用一个真实小项目或当前 repo 的干净副本，不用空目录。
- 看到 CLI daily workflow 引导时记为摩擦；CLI 只可作为安装、自检、维护兜底。
- 不把 benchmark 分数、token/cost saving、latency、answer-quality 写成产品结论，除非对应 gate ready。

### 角色卡

- 29 岁，深圳，AI infra 工程师。
- 偏好 Codex desktop，因为能直接看文件 diff 和测试输出。
- 主要痛点：切换 session 后要快速恢复项目约定，不想读一堆 roadmap。
- 投入度：高，愿意读 docs/roadmap-status.md，但不愿读实现源码。

### 你被允许读的文档

- README.md
- docs/roadmap-status.md
- plugins/harness-mem/README.md
- plugins/harness-mem/commands/hm/status.md
- plugins/harness-mem/commands/hm/wake.md
- plugins/harness-mem/commands/hm/search.md
- plugins/harness-mem/commands/hm/distill.md

### 环境准备

- Codex 已安装 harness-mem MCP。
- 当前工作区是一个已有 session 历史的项目。

### 执行步骤

- Step 1: 让 Codex “用 harness-mem 看当前项目状态”。记录: 是否返回 `next_actions`、`why_this_result`、`degraded_reason`，你是否知道下一步该 wake 还是 distill。
- Step 2: 让 Codex “用 harness-mem 唤醒当前项目”。记录: `wake` 是否返回可直接读的 context、`drilldown_hints` 是否指向可复查 source。
- Step 3: 让 Codex 搜索一个真实任务相关主题。记录: `search_memory` 是否解释结果来源，是否出现 CLI daily command 叙事漂移。
- Step 4: 让 Codex 整理最近 session 并自动审核候选。记录: agent 是否走 `prepare_session_distill -> suggest_* -> auto_review_candidates(apply=true)`，还是错误地让你去终端跑 CLI。
- Step 5: 触发 maintenance preview。记录: no-op 项目是否明确返回“没有需要维护的东西”，还是空输出。
- Step 6: 对本次 search 的两个 source 记录 `used` / `ignored` outcome。记录: 返回是否明确 `truth_mutated=false`。

### v5.6 关注点

- Daily flow 是否 5 分钟内跑通。
- evidence 只作为 gate，不变成用户叙事主角。
- outcome signal 是否可解释且不改 truth。

## Persona B: 周玥（Claude Code，slash-first）

### 角色卡

- 34 岁，杭州，后端工程负责人。
- 偏好 Claude Code slash command，因为团队内部已有 `/hm:*` 习惯。
- 主要痛点：维护功能听起来危险，需要确认可撤销、有 ledger、默认不后台跑。
- 投入度：中高，愿意读插件命令文档，不读 benchmark-suite。

### 你被允许读的文档

- README.md
- plugins/harness-mem/commands/hm/status.md
- plugins/harness-mem/commands/hm/wake.md
- plugins/harness-mem/commands/hm/search.md
- plugins/harness-mem/commands/hm/distill.md
- plugins/harness-mem/commands/hm/dream.md
- docs/roadmap-status.md

### 环境准备

- Claude Code 已配置 harness-mem MCP / slash commands。
- 选择一个有 pending candidates 或历史 truth 的项目。

### 执行步骤

- Step 1: 输入 `/hm:status`。记录: 输出是否像“下一步建议”，而不是裸状态列表。
- Step 2: 输入 `/hm:wake`。记录: wake 内容是否足够回答“我现在该注意什么”。
- Step 3: 输入 `/hm:search <真实主题>`。记录: 搜索结果是否包含 why / drilldown / degraded 信息。
- Step 4: 输入 `/hm:distill <project> 10` 或自然语言等价入口。记录: 自动审核摘要是否说明 auto-confirm、auto-reject、待人审项。
- Step 5: 输入 `/hm:dream` 或等价维护入口。记录: 是否出现 preview -> apply -> ledger -> undo 的一屏摘要。
- Step 6: 尝试 undo 一个已应用 dream item。记录: undo 是否有 ledger item 和明确结果。

### v5.6 关注点

- 维护体验是否低恐惧。
- 所有 truth 变化是否仍走 candidate / review / supersede / ledger。
- scheduler / host hook 是否仍默认 off，只给 opt-in 指引。

### 执行步骤

- Step 4: 制造一个错误输入，例如缺 project_name 或空 source_ids。记录: 错误是否包含原因和可执行修复。

## 三个以上 persona 跑完之后

| 分类 | 判定规则 | v5.6 处理 |
|---|---|---|
| 真问题 | 两个以上客户端都卡在同一步，或 MCP schema/handler 失败 | P0 修实现或工具 schema |
| 客户端特定 | 只有一个客户端入口文案或配置卡住 | 修对应 slash / skill / plugin doc |
| Persona-specific | 只影响某个低频工作方式，不破坏主路径 | 进入后续 roadmap，不阻塞发版 |
| README / claim mismatch | 文档承诺超出 benchmark/release gate，或包装 token/cost saving | P0 文档修正，继续保留 blocked claim |

## Release Gate 记录

- `benchmark_matrix_report` 必须通过。
- `context_outcome_loop` loop harness 必须通过。
- field-test 每个 persona 至少完成 status / wake / search / distill 或 maintenance / failure recovery 中的一条主路径。
- 如果 `token_cost_saving.ready=false`，继续写 blocked，不能包装成“省钱”。
